01 — A few numbers go in

Start with something
you can name.

A model takes numbers as inputs. They might describe a sensor reading, a candidate search result, or—in our tiny example—whether two switches are on.

Connections multiply those inputs by weights. A bias adds an offset. An activation function shapes the result. Repeat that across a few layers, and you have a small neural network.

Input
A number you give the model.
Weight
A number that changes a connection’s influence.
Prediction
The result of running the math.

02 — Learn from examples

Training turns
the knobs.

Show a model examples with the answers you want. Compare its predictions with those answers. An optimizer adjusts the weights to reduce the error, then tries again.

The JavaScript SDK supports SGD and AdamW training through real Rust-built WebAssembly. Prepare the resulting checkpoint once, then reuse it for predictions across batches.

↳

A checkpoint is simply a saved model: its structure, weights, biases and activation settings.

03 — Make a precise intervention

Sometimes you want
to turn one yourself.

Weight-space programming means inspecting and directly changing a model’s parameters. A person, an algorithm or an agent can propose the edit.

With ruv-fann-wsp, the edit is a small, structured patch. It names the exact weight or bias to replace and the fingerprint of the model it belongs to.

The patch preserves the network’s structure. It is still a proposal: changing a number does not tell you whether the behavior got better.

One connection0.00 → 1.00Same network. A different answer.

04 — Measure before you keep it

A change earns
its place.

Run the original model and the candidate on the same evaluation cases. Check the error and your regression limits. Keep the candidate separate while you inspect the result.

Promotion is an explicit action. An accepted, current proposal can become the active checkpoint. Rollback restores a retained checkpoint as a new revision.

For real tasks, keep unseen evaluation cases away from whoever chooses the edits. A passing score describes those cases; it does not prove generalization.

02 / THE WORKBENCH

Open the model.
Ask a better question.

Version 0.2.0 adds four ways to understand a small model before changing it. Each observation stays tied to the checkpoint it describes.

01

Look at the structure.

See the layer dimensions, activation settings and parameter counts. Get a canonical fingerprint for the checkpoint.

inspectWeightModel()
02

Follow a signal.

Trace the values before and after each activation. Both passes use the actual WASM engine’s calculations.

traceWeightModel()
03

Disconnect one unit.

Zero a hidden neuron’s outgoing connections, then measure what changes. The result is a normal hash-bound patch.

04

Estimate sensitivity.

Nudge selected parameters up and down, and compare the measured error. This is a local numerical estimate, not autograd.

analyzeWeightSensitivity()

Start with a model

This complete example traces a one-layer model computing y = 2x + 1. Save it as inspect.mjs and run node inspect.mjs.

1. INSTALL THE WORKBENCH
npm install ruv-fann-wsp

The exact core and WASM dependencies arrive with it. Then create the example file shown here.

2. RUN YOUR FILE
node inspect.mjs

Expected activations: [3, 5, 7]. Tracing observes the model; it does not train or change it.

Next: a complete patch + promotion example ↗
● ● ● inspect.mjs
import {
  inspectWeightModel,
  traceWeightModel
} from 'ruv-fann-wsp';

const model = {
  schema: 'ruv-fann.dense-layers/1',
  layers: [{
    inputs: 1, outputs: 1,
    weights: [2], bias: [1],
    activation: 'Linear', steepness: 1
  }]
};

const info = await inspectWeightModel(model);
const trace = await traceWeightModel(model, {
  inputs: [1, 2, 3], rows: 3
});

console.log(info.parameterCount); // 2
console.log(trace.layers[0].activations);
// [3, 5, 7]

A FEW USEFUL DISTINCTIONS

Before you
build.

Does weight-space programming replace training?

It gives you another way to create or adapt a checkpoint. Training adjusts parameters using an optimizer and examples. WSP applies explicit parameter edits. The useful choice depends on the task, data and evaluation budget. The package provides the tools; it does not promise direct edits will outperform training.

Is the workbench automatically learning or calling an LLM?

No. A caller supplies the model, edit and evaluation cases. No model provider is built in, and retrieval does not trigger automatic updates. An agent can use the API through its own orchestration, with explicit evaluation and promotion.

What does the fingerprint protect?

A patch’s SHA-256 fingerprint identifies the canonical checkpoint it was written for. A mismatched patch is rejected. Hashes bind content; they are not signatures and do not authorize promotion. A workspace uses its internally retained accepted proposal and current revision for that decision.

Does this page demonstrate GPU acceleration?

The live experiment uses CPU WebAssembly, with SIMD when supported. The repository also has separate optional WebGPU compute paths. Their software-adapter correctness checks do not establish physical GPU throughput. See the core review and feature limits before choosing a backend.

What should I evaluate for an actual application?

Use representative cases, separate model/edit selection from final evaluation, and check regressions that matter to your users. Record dataset provenance, model hashes, runtime and policy. MSE is the WSP workbench’s supplied numeric metric; an application may also need task success, ranking quality, calibration or other criteria.

Can I persist the workspace?

The package’s workspace history is in memory. Save checkpoints yourself or use the AgentDB integration for durable models, proposals and revisions. Keep application access controls and concurrency limits around mutations.
